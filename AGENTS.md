# Working in RoleSail

This file is a map, not a substitute for reading the code. Before changing anything, inspect the current implementation, its callers, the data it reads and writes, and the relevant tests. Use [README.md](README.md) for product behavior and setup, and [CONTRIBUTING.md](CONTRIBUTING.md) for the contributor workflow; when those summaries disagree with executable configuration or current code, follow the latter and update the documentation if it is in scope.

## Architecture

RoleSail is a Python 3.11+ local-first application with two user interfaces: a Typer CLI and a bundled React dashboard. User state lives outside the repository in `~/.rolesail` by default, or under `ROLESAIL_DIR`. The `APPLYPILOT_DIR` environment variable and `applypilot` console command are intentional migration compatibility surfaces.

- `src/rolesail/cli.py` is the public command boundary. Keep argument validation, prerequisite checks, and user-facing Rich output here; delegate work to the modules below. `src/rolesail/__main__.py` and the scripts in `pyproject.toml` both enter through the Typer app.
- `src/rolesail/pipeline.py` orders and coordinates the discover, enrich, score, tailor, cover, and PDF stages. In streaming mode, the SQLite database is the conveyor belt between concurrent stages. Preserve each stage's ability to run independently and keep pending-work queries consistent with the states written by stage implementations.
- `src/rolesail/discovery/` owns external job-source adapters and early title/location filtering. Adapters should normalize source payloads to the shared job fields and use shared filtering, retention, HTTP, and persistence helpers where applicable. Employer/ATS registries and source policy live in `src/rolesail/config/*.yaml`; do not embed registry data in adapters without a source-specific reason.
- `src/rolesail/enrichment/` resolves canonical application URLs and full descriptions for accepted jobs. URL normalization and extraction fallbacks belong here rather than in the UI or discovery-specific presentation code.
- `src/rolesail/scoring/` owns LLM scoring, resume/cover-letter generation, validation, LaTeX handling, and PDF conversion. Keep factual-preservation and rendered-output validation intact when changing tailoring. Provider selection, pacing, and request accounting are centralized in `src/rolesail/llm.py` and `src/rolesail/usage.py`.
- `src/rolesail/database.py` is the shared persistence boundary. It owns SQLite connections, schemas, additive migrations, retention, stage queries, and common writes. Connections are thread-local and use WAL because stages and workers run concurrently. A jobs-column change must be represented in both the new-database schema and the additive column registry, with upgrade coverage; do not scatter ad hoc schema migration logic through feature modules.
- `src/rolesail/apply/` owns autonomous application execution: Chrome lifecycle, Claude/Playwright-MCP launching, prompt construction, atomic queue acquisition, and worker status. Keep external-process and browser concerns behind this layer. Application status transitions also trigger or cancel outreach, so trace those side effects before changing them.
- `src/rolesail/outreach/` owns the post-application workflow. `service.py` is the domain coordinator and durable state machine; `apollo.py`, `gmail.py`, and `research.py` are external-integration boundaries. Keep draft creation review-gated and preserve retry/idempotency behavior. Do not move provider-specific calls into dashboard handlers.
- `src/rolesail/dashboard_server.py` is the local HTTP/controller boundary and static-file server. It validates requests, starts background work, maps domain errors to JSON responses, and calls service functions. `src/rolesail/dashboard_data.py` builds the dashboard's read model and should remain free of HTTP and markup concerns.
- `frontend/src/api.ts` is the SPA's API boundary and `frontend/src/types.ts` defines response shapes. Page/feature components own presentation and local interaction; TanStack Query owns server-state fetching and invalidation. When an API contract changes, update the Python handler/read model, TypeScript client/types, and tests together.
- `src/rolesail/config.py` owns runtime paths, defaults, feature tiers, environment loading, and package-config access. User profile, resume, searches, database, OAuth material, logs, and generated application artifacts belong under the configured application directory—not in source control.

`src/rolesail/web_dist/` is generated by the Vite build and is committed so the Python package can serve the dashboard without Node.js. Edit `frontend/`, then regenerate the bundle; never hand-edit hashed assets or `web_dist/index.html`. Likewise, do not edit caches, `frontend/node_modules/`, `frontend/test-results/`, `*.tsbuildinfo`, runtime databases, or files under the user's application directory. Treat `frontend/package-lock.json` as npm-managed.

## Before and during a change

Firm requirements:

1. Establish the intended user-visible behavior or reproduce the bug before selecting an implementation. Read this file first, then inspect the relevant current code, callers, dependencies, persisted fields or API payloads, and tests.
2. Place the change in the layer that owns the behavior. Reuse or extend an existing helper or service when its contract genuinely fits; search before adding a parallel implementation. Do not bypass `config.py`, `database.py`, the LLM/usage layer, integration adapters, or `frontend/src/api.ts` with a second source of truth.
3. Trace affected interfaces and state transitions end to end. In particular, consider partial external failures, retries, thread safety, SQLite transactions, stage re-runs, stale/legacy data, dashboard background jobs, and ApplyPilot-to-RoleSail compatibility where relevant.
4. For a substantial or cross-layer change, briefly state the proposed behavior, affected modules, boundary changes, and important tradeoffs before editing. Proceed directly on routine, well-scoped work. Ask only when an ambiguity materially changes correctness, public behavior, data compatibility, or scope; resolve ordinary implementation details independently.
5. Make the smallest coherent change that fully solves the task. Do not mix in unrelated cleanup, speculative features, or broad rewrites. New dependencies need a concrete benefit that existing dependencies or the standard library cannot reasonably provide.
6. Check usages before removing or renaming anything. Remove code and compatibility branches made genuinely obsolete by the change, but retain public CLI options, API shapes, persisted data handling, and migration aliases unless the task explicitly changes them.

Prefer cohesive feature or layer modules with explicit inputs and outputs. Avoid adding more responsibility to already broad coordinators such as `dashboard_server.py`, `pipeline.py`, or `outreach/service.py` when a focused existing module owns the behavior. Conversely, do not fragment a simple flow into tiny single-use files or create generic `utils` catch-alls. A local helper is preferable until multiple callers share a stable concept.

Follow established patterns deliberately, not mechanically. Architectural cleanup is welcome when it is necessary to make the requested change safe or understandable, but explain why it is needed and keep it proportional. Isolated legacy inconsistencies are not a mandate to reproduce them.

## Configuration, errors, and observability

- Use `logging.getLogger(__name__)` for diagnostics and failures. Rich/`print` output is for user-facing CLI or server lifecycle messages, not a replacement for logs in library code.
- At external and HTTP boundaries, validate inputs and turn expected failures into useful errors. Preserve context when logging unexpected exceptions. Do not silently convert failures into apparent success; pipeline stages intentionally record/report partial failures and retryable states.
- Keep configuration in the existing owner: runtime defaults and paths in `config.py`, user choices in the application directory, and shipped source registries in `src/rolesail/config/`. Never commit real credentials, OAuth tokens, resumes, profiles, databases, or personal application artifacts. Tests should use temporary directories and fake integrations.
- Preserve idempotency where operations may be retried: database initialization/migrations, discovery upserts, imported-job enrichment, application claims, and outreach/draft actions are all restartable workflows.

## Documentation

Document public contracts, non-obvious behavior, invariants, compatibility constraints, and the reason for consequential decisions. Use the repository's concise Python docstring style and TypeScript naming conventions. Comments should explain why a guard, state transition, or workaround exists—not narrate the next line. Do not add boilerplate docstrings to trivial private helpers or restate types in prose.

Update existing docs when behavior, CLI/API contracts, configuration, prerequisites, setup, or architecture changes. Prefer linking to `README.md` or `CONTRIBUTING.md` over duplicating long operational instructions here, and remove or revise stale comments as part of the change.

## Tests and verification

Install the Python development environment with:

```bash
pip install -e ".[dev]"
```

The normal backend checks, matching CI, are:

```bash
ruff check src/
pytest tests/ -v
```

For a focused iteration, run the relevant test module first, for example `pytest tests/test_scoring.py -v`, then broaden according to risk. `ruff format src/` is the configured formatter command; `pyproject.toml` is authoritative for Ruff settings (currently Python 3.11 and a 120-character line length). There is no configured Python static type-check command.

Dashboard development requires Node.js 20.19+ and dependencies installed from `frontend/` (`npm install`; use the lockfile). Available checks are:

```bash
cd frontend
npm test
npm run typecheck
npm run lint
npm run build
```

`npm run build` writes committed production assets to `src/rolesail/web_dist/`. Use `npm run build:check` before release or whenever the submitted bundle must be proven current; it rebuilds and fails if the bundle differs from Git. Run `npm run test:e2e` for browser/API integration changes; it starts `python -m rolesail dashboard` on port 8766, uses `/tmp/rolesail-playwright`, and requires the editable Python package plus Playwright Chromium (or `CHROME_PATH`). The publish workflow additionally runs `python -m build`, which requires the `build` package.

Add or update tests for changed behavior, especially a regression test for a bug. Backend tests conventionally use pytest fixtures, `tmp_path`, `monkeypatch`, and fake network/LLM clients; frontend component tests use Vitest, Testing Library, and MSW; `frontend/e2e/` covers the packaged dashboard boundary. Assert observable contracts and durable state transitions rather than private call order or copied implementation logic. Do not make routine tests depend on live job boards, LLMs, Apollo, Gmail, Chrome profiles, or user data.

Choose checks in proportion to the change: backend-only work need not rebuild the SPA; frontend behavior should run its focused tests plus typecheck/lint and regenerate `web_dist` when production assets are part of the change; cross-boundary work should exercise both sides. Never claim a check passed unless it ran. At handoff, report what changed, why it belongs in the chosen layer, the exact checks run, and any unverified paths or remaining limitations.
